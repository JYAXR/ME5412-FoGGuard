# ME5412 FoGGuard

FoGGuard 是一个为期三周的 ME5412 小组项目，研究如何结合冻结步态（Freezing of Gait，FoG）相关信号与步行情境，提供投影脚印和声音节奏组成的可解释提示。最终成果是一个可复现、可量化评估的离线 Streamlit 演示原型。

项目的目标应用人群是存在 FoG 的帕金森病患者；本期原型的直接使用者是项目组、教师与评审，使用合成数据理解和检验工程流程。本期不进行患者试用，不是医疗器械，也不用于实时临床决策。

## 课程要求与选题对应

依据团队提供的《ME5412-2026 Project Assignment Briefing》：第 4 页明确不要求实体原型，交付重点是 concept/design/simulation；第 6 页包含 mobility aids 和 assistive technologies；第 7 页允许新界面、控制算法或软件架构，同时要求问题与创新具体，避免技术愿望清单。因此本项目定位于冻结步态行动辅助的交互与控制方案，采用数据回放和策略仿真展示。

正式汇报为 **10–15 分钟，另有 5 分钟问答**（第 8 页）；**2026 年 11 月 3 日提交幻灯片作为报告**（第 4 页）。五分钟软件演示仅作为汇报片段。第 8 页的“Close the loop!”在本项目中落实为问题、方案、验证与局限的对应关系；说明未明确要求真实人体或硬件反馈闭环，也未要求真实患者数据。以上为该说明所载要求，不代表教师已批准本组具体方案或给出评分承诺。

## 项目目标与研究问题

产品问题：患者冻结时，系统如何给出能够完成的下一步？恢复行走后，如何根据完成情况调整脚印位置与提示强度？系统应解释何时提示、怎样提示以及何时退出。

项目目标：在既有数据回放和 FoG 检测基线上，明确情境自适应 cueing 的需求，形成可由各模块负责人实现、由评估负责人验证的离线原型。检测性能、提示策略行为与临床疗效分别讨论。

| 研究问题 | 本期需要提供的证据 |
|---|---|
| RQ1：FoG 检测在不同场景中的误报、漏报和延迟如何？ | 分场景的窗口级指标、事件级延迟及失败案例；说明合成数据限制 |
| RQ2：系统能否识别直走和左右转弯，并表达情境不确定？ | 情境标签与识别结果对照；当前转向状态识别不能直接称为提前意图预测 |
| RQ3：按情境和事件阶段调整脚印与声音，相对固定提示有何工程差异？ | P0 比较触发、退出、方向和延迟；P1 分别比较固定/自适应间距、直接迈步/踏步备用及持续/渐弱提示；只评价工程行为与假设敏感性 |

文献依据：Cosentino 等（2023）的综述将任务区分为起步、行走与转弯，提示方式对不同步态指标的影响有所不同。该结果支持分别设计和评估场景；并未证明本项目的具体策略有效。步态参数改善也不能直接等同于 FoG 减少。详见 [One cue does not fit all](https://doi.org/10.1016/j.neubiorev.2023.105189)（DOI：10.1016/j.neubiorev.2023.105189）。

## 产品方案（目标需求）

主要输出为地面投影脚印和声音节奏，直行与转弯都可使用；情境差异体现在脚印路径、方向和提示时序，而不要求转弯必然切换触觉。实体投影方式尚未选型；本期只做屏幕上的目标与提示演示。

- **冻结与重新启动**：先给出个人可完成的明确迈步目标；仍不能启动时，可选择原地左右交替踏步提示，再引导向前。踏步是备用策略，先后顺序可配置，不要求所有人每次使用。
- **恢复行走**：根据最近几步的完成情况，在个人目标范围内调整下一步脚印；不按固定时间一直增大，也不随碎步无限缩短。
- **稳定阶段**：探索逐渐减弱视觉清晰度和声音音量；保留持续提示选项。冻结时恢复已配置的提示，不自动加快节拍或要求更大步。
- **目标稳定**：正在迈向的脚印保持位置不变，确认落脚后才调整下一步；转弯同时考虑朝向、左右间距和路径。
- **能力边界**：低 FoG 评分不能单独证明平稳行走或成功迈步。踏步恢复、自适应间距及渐弱规则是待验证设计，不能宣称已获得临床验证。

## 当前实现与本期范围

以下状态基于 2026-10-18 对代码的检查，表示已有实现，不等于本次已重新运行或完成验收。

| 部分 | 已有基础 | 待完成的需求 |
|---|---|---|
| 数据 | 合成场景生成、CSV 读取、窗口回放与 FoG 标签对齐 | 补充左右转、正常转弯、主动停步、恢复及异常输入场景 |
| FoG | 频带能量评分、阈值判断、窗口级评估与阈值标定 | 事件级评估与失败分析；当前评分不是经校准的临床概率 |
| 情境 | 根据平均角速度识别左转、右转和直行 | 可靠性与不确定情境处理；没有起步困难或步长估计能力 |
| 提示 | 转向 FoG 选择触觉，其余高评分输入选择声音；有不应期判断 | 完整接入提示历史、恢复退出和输入降级；现有模态映射只是基线 |
| 展示 | FoG 评分曲线和包含转向、提示类型的结果表 | 增加屏幕脚印、声音提示状态、决策原因、事件阶段和功能局限 |
| 验证 | 数据、检测、标定、评估与模块连接的基础测试 | 情境和提示行为验收；完整指标与错误分析 |

优先级约定：P0 为本期必需；P1 为 P0 完成后的探索；Future 为后续方向。以下是需求范围，不表示功能均已实现。

- **P0**：保留正常行走、直行 FoG、转向 FoG 的离线回放和检测评估；补齐左右转向、提示原因、恢复退出、不应期及异常降级。在屏幕演示固定配置的脚印与声音提示状态，明确哪些由检测驱动、哪些是给定路径。无需本期实现真实步长/位置估计或投影硬件。
- **P1**：用明确标注的模拟落脚/响应输入，分别探索踏步备用策略、下一步目标间距调整、稳定后渐弱与冻结后恢复。缺少相应输入时禁用自动调整；不能将脚本输入算成自动识别能力。
- **Future**：可靠的实测步长和落脚位置、稳定性评估、投影定位与同步、真实硬件闭环及人体研究。个性化临床参数需要独立验证。

## 数据如何继续使用

现有 CSV 含时间、三轴加速度、三轴角速度以及 FoG/转向标签，支持检测、转向和提示时序评估；详情见[数据格式](docs/DATA_SCHEMA.md)。四个演示文件由同一生成器产生，包含正常、直行冻结、转向冻结和混合时间线，属于合成信号，不是患者记录。

| 数据或输入 | 本期用途 | 不能据此证明 |
|---|---|---|
| 现有 IMU 信号与独立标签 | 驱动检测与转向模块，计算误报、漏报、F1、检测及提示延迟 | 患者获益、真实步长或精确落脚位置 |
| 明确标注的模拟落脚、步幅及响应事件（尚待实现） | 检查脚印更新、踏步切换、渐弱与恢复的规则和异常处理 | 自动感知准确率、患者一定会照提示行动 |
| 未来符合使用条件的真实数据 | 经核查采样率、单位、传感器位置和标签后验证相应模块 | 未采集提示反应时，不能比较干预疗效 |

离线录制数据不会因系统发出提示而改变。若加入模拟患者响应，必须声明模型假设，并测试无效、延迟响应和恶化等情况；仿真中的“冻结缩短”只能解释为模型下的结果。

## 三周最小可行成果（MVP）

现有流程：CSV / synthetic replay → FoG 与转向基线 → 提示命令 → Streamlit 展示；FoG 窗口级评估与阈值标定已有独立脚本。

目标流程：数据质量检查 → FoG 判断与步行情境识别 → 按情境及事件阶段选择提示 → 解释决策、记录时间线 → 对照评估。

完成标准：

1. 新成员能按下方命令启动演示并复现实验。
2. P0 场景有输入、标签、预期行为及验收记录。
3. 每次提示或不提示都能解释原因；屏幕脚印与声音状态对应控制输出，恢复、重复触发和异常输入行为可检查。
4. 最终报告包含分场景检测指标、情境结果、提示时序与失败案例，区分已有证据和待验证假设。

具体需求与验收口径见[系统架构与需求](docs/ARCHITECTURE.md)，负责人及交付顺序见[分工与三周路线图](docs/ROLES_AND_ROADMAP.md)。

## 快速开始

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .
streamlit run src/fogguard/ui/app.py
```

使用 `python scripts/generate_demo_data.py` 生成小型演示数据；使用 `pytest` 和 `ruff check .` 进行检查。

生成数据后，可以重复运行 FoG 基线评估：

```bash
python scripts/evaluate_fog_baseline.py
python scripts/calibrate_fog_threshold.py
```

评估命令会按场景输出窗口数量、真实/预测 FoG 窗口数，以及 accuracy、precision、recall 和 F1。标定命令会用预先声明的规则选择阈值，并将本地报告写入 `reports/fog_threshold_calibration.json`。当前合成场景标定得到 `0.21`；它只用于检查工程管线，不代表临床性能。标定记录中的 F1＝1.00 表示这些合成数据上的窗口分类没有误报或漏报，不能解读为真实患者检测准确率达到 100%。开发与留出场景来自同一生成器，详见[阈值标定记录](docs/FOG_THRESHOLD_CALIBRATION.md)。

## 模块接口约定

所有模块通过 `fogguard.types` 中的数据类交换信息：

- `SensorWindow`：单个 IMU 窗口；加速度采用 m/s²，角速度采用 deg/s，时间采用秒。
- `DetectionResult`：FoG 评分、布尔判断及可选判据；现有字段名为 `probability`，尚未经概率校准。
- `TurnIntent`：方向、置信度及时间范围字段；当前实现依据窗口角速度，不具备已验证的提前预测能力。
- `ControllerContext`：当前预测、时间信息和不应期状态。
- `CueCommand`：提示类型、强度、持续时间和可读原因。

实现必须满足 `fogguard.interfaces` 中的协议。各功能分支可以替换基线模型，但不应迫使下游代码同步重写。任何接口修改都必须先建立 Issue、征得相关负责人同意，并更新 `docs/ARCHITECTURE.md`。

## 团队协作方式

1. 先认领一个 GitHub Issue，再创建简短分支，例如 `feat/fog-baseline`。
2. Pull Request 保持小而清晰，并用 `Closes #<编号>` 关联 Issue。
3. 合并到 `main` 前至少由一位组员审查。
4. 严禁提交可识别参与者身份的数据；本地原始数据放在已忽略的 `data/raw/`。
5. 每天结束前更新 Issue 清单并记录阻塞事项。

详细内容见[分工与三周路线图](docs/ROLES_AND_ROADMAP.md)、[协作规则](docs/COLLABORATION.md)和[系统架构](docs/ARCHITECTURE.md)。

## 安全与项目边界

本仓库仅用于课程项目和工程评估，不用于诊断、预防或治疗疾病。需求要求输入缺失、过期或相关判断不可靠时返回 `CueType.NONE`；当前实现尚需按架构文档补齐并验收。任何涉及人体参与者的数据采集都必须在仓库之外先取得教师同意及适用的伦理审批。
